## The driver

`campaign_control_rev6.ipynb` is the only driver of the calibration campaign. On each machine it configures the run, builds the solver, checks the machine against the reference, starts the worker, monitors it against the experimental data, and stops or restarts it. The commands below are what it runs.

## Ranking the parameters

```bash
# once, on one machine; then commit design/
python design.py --tier 2 --N 16 --out design/T2_design_v1.csv

# on each machine k of M
python run_ensemble.py --design design/T2_design_v1.csv --machine k --of 4 --workers 10 \
                       --I 800 --V 600 --dose 0.1

# anywhere, after pulling the results
python merge_and_sobol.py --design design/T2_design_v1.csv --results results/
```

- Machine k runs every row whose `row_id` modulo M equals k. There is no coordination and no shared file system, and a restart skips the rows already written.
- With `--weights`, machines of unequal speed take unequal shares. The weights are frozen in `machines.json`: changing one would give rows already computed to another machine.
- Each machine writes its own result file, so the files never conflict and git carries them.
- `merge_and_sobol.py` reports the coverage and refuses to estimate an index from too few rows. `test_sobol.py` validates the estimator against the Ishigami function, whose indices are known.

## Calibrating

The target is one parameter vector that puts six observables inside their measured ranges for EUROFER-97 at 330 °C and 15 dpa under neutron irradiation: the number density and mean diameter of ⟨100⟩ loops, of ½⟨111⟩ loops and of cavities.

The loop is `learn.py` → `plan.py` → `run_ensemble.py` → `verify.py`:

1. `learn.py` reads the result files and derives what each parameter moves, from pairs of rows that differ in exactly one parameter.
2. `plan.py` proposes the design of the next stage and prints the command for this machine. It is a dry run unless `--write` is given, and it never starts a run.
3. `run_ensemble.py` runs it.
4. `verify.py` reruns the best rows on a larger grid. An observable counts only when it survives that change.

The calibrated vector is the default of the workbook, and the notebook reproduces it as the reference case.

## Verifying the approximations

`verification/` runs the study planned in `docs/Formulation/verification_campaign/paper_revision_verification_plan.md`.

| File | Role |
|---|---|
| `runs.py` | the manifest: one entry per table cell, with the shared output grid and the dose each run is read at |
| `campaign.py` | runs the study one claimed run at a time (`--loop`, or `--run <name>`) |
| `gitsync.py` | coordination over git: a machine claims a run, and publishes its result, by pushing to the remote |
| `rescore.py` | re-applies the observation step to runs already computed |
| `make_tables.py`, `make_M_report.py`, `make_M_latex.py`, `make_M_figures.py` | the tables and figures, written into `docs/Formulation/verification_campaign/` |

The claims and results live on the orphan branch `campaign-verification`, which shares no history with `main` and holds no source. It is used through a git worktree, `verification/.sync/`, so that a pull never changes a file under a running solver.

A run that did not reach its comparison dose is never printed as a value; the tables list it with the dose it reached.

## Rules the campaign enforces

| Rule | Reason |
|---|---|
| The design is generated once and committed. `run_ensemble.py` refuses a design whose SHA-256 does not match its sidecar, when it has one | Saltelli indices are computed from paired rows; machines that sample independently destroy the pairing, and the indices are then wrong, not noisy |
| Every machine passes `check_machine.py` before it joins | each machine compiles its own solver, and different compiler or SUNDIALS versions give different numbers. The check compares twelve quantities with the reference at a relative tolerance of 10⁻⁶, the integration tolerance of the probe; one binary repeats exactly, and identical source differs by about 10⁻⁷ between architectures |
| Every row records `git_sha`, `solver_sha256`, `workbook_sha256`, `design_sha256` and `machine_id`. The merge warns of a split when machines disagree on the workbook, the design, the run configuration or the weights; a different commit or solver hash is only noted, since each machine builds its own solver | results of different inputs must not be pooled |
| A failed row of one parameter's set is dropped from the estimator of that parameter only; a failed base row is dropped for all | deleting more than that would bias every index |
| A row that reaches its time limit is kept, with the observables at each dose it reached | the solver stops gracefully and writes its trajectory. Rows are then compared at a common dose (`--at-dose`), never at the dose each happened to reach |
| Workers run single-threaded (`OMP_NUM_THREADS=1`), many at a time | better throughput for an ensemble, and the same order of floating-point sums on every machine |
| The stop flag is local | `campaign_ops.request_stop()` writes a file that only the workers of that machine read; stop each machine separately |

## What a row measures about the grid

A row carries, besides its observables, measures of whether the size grid was large enough: the fraction of the content in the top 2 % of the grid (`pile_111`, `pile_100`), the fraction in the top bin (`topbin_111`, `topbin_100`, `topbin_v`), the dose reached, and the two conservation residuals.

δ_FP is not a test of the grid. The growth of ⟨100⟩ loops is halted at the top of the grid without losing atoms, so a ⟨100⟩ distribution stacked there leaves δ_FP small; truncation on the vacancy axis and loss of ½⟨111⟩ products beyond the grid do raise it. Judge the grid by the content near its top.

Since 5 August 2026 these measures are recorded on every row but reject none: a row is admissible when it ran and reached its dose. `merge_and_sobol.py --require-converged` restores the earlier rule, so that a ranking can be checked both ways.
